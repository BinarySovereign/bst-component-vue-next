# 技法与反模式

`SKILL.md` 讲的是流程，这里讲的是「同样一个块，怎么写才真的起作用」。

---

## 1. 让约束真正生效

**解释原因，而不是堆 MUST。** 现代模型对「理解了原因的约束」遵守得更好。写「不要引入新依赖，因为这个包要在离线环境构建，装依赖会破坏现有的 lock 文件一致性」，比写「NEVER add dependencies」更可能被遵守。反过来，通篇大写 MUST / NEVER / 严禁，会让所有约束一起贬值——包括那条真正重要的。

**规则数量和遵守率成反比。** 一条提示词里塞进十几条规范，模型会挑几条执行、随机忽略几条，而且被忽略的往往不是最不重要的那条。逐条自问「删掉它，输出会变差吗」，答案是否就删。红线是 5~7 条，超了就该拆分任务或改用具象的范例替代抽象规则。

**正向范例胜过负面禁令。** 「参考 `src/utils/date.ts` 的错误处理写法」比「不要吞掉异常」有效得多，因为范例同时给出了正确做法和判断依据。能用「照这个来」的地方，就别用「不许那样」。

**约束要落在可观测层面。** 「代码要健壮」不可观测；「所有外部输入在入口处校验，非法输入抛 `TypeError` 而不是返回 null」可观测。判断标准：模型能不能自己检查有没有做到？不能，就是没写。

## 2. 上下文工程

**执行者能读仓库，所以给线索，不给全文。** 这是最容易搞错的一处：把源码整段贴进提示词，会直接挤占 Agent 的探索与推理预算，常见后果是它只盯着你贴的那几十行，不去看周边。

- 给**位置与线索**：文件路径、符号名、可参照的现有实现、要跑的命令、用于检索的文件模式。
- 只有一类材料必须内联：**无法靠描述精确复现的东西**——报错栈、日志、测试失败输出、设计稿。这类材料贴原文，不要转述成「报了个类型错误」；转述丢掉的信息，模型补不回来。
- 少量内联时同样做减法：删掉与问题无关的部分，并**明确告诉模型「为简化起见省略了 X」**，否则它会基于不完整的代码做出错误推断。

**报错原文必须内联。** 错误栈、日志、测试失败输出，属于「无法靠描述精确复现」的材料，永远贴原文，不要转述成「报了个类型错误」。

**上下文是预算，不只是信息。** Agent 的上下文窗口会被读过的文件和命令输出快速填满，填满后早期指令会被遗忘。所以：任务之间用 `/clear` 或新会话；大范围调研交给子代理/独立上下文；调研范围要收窄（「让 Claude 调研」而不限定范围，它会读几百个文件把自己填爆）。

## 3. 防编造与证据要求

编码场景里模型最常编的三样东西：**API 签名、库版本行为、文件路径**。三招应对：

1. **显式兜底条款**：「不确定的 API / 版本行为先查源码或官方文档确认，不要凭记忆写；查不到就说查不到。」
2. **要求证据而非声称**：「完成后贴出实际执行过的命令与返回」，比「确保测试通过」有用一个量级——后者模型会直接回复「已完成」。
3. **要求区分已知与推测**：让它把「已验证」和「按经验推测」分开标注。这条在方案设计类任务里尤其重要。

一个更狠的变体是**让干活的人不自评**：把审查/验证交给另一个干净上下文的会话或子代理，只看 diff 和验收标准，不看产生改动的推理过程。自评会倾向于为已经写出的代码辩护。

---

## 4. 计划与执行的控制

**什么时候要求先计划：** 方案不确定、改动跨多文件、对涉及代码不熟。这时让模型先给实施计划并**等你确认**，再动手。计划本身是廉价的，改计划比改代码便宜得多。

**什么时候直接做：** 一句话能描述 diff 的小改动。这时要求「先给计划」纯属浪费轮次。

**两次法则。** 同一个问题纠正超过两次，说明上下文已经被失败方案污染，继续纠正通常是负收益。正确动作是清空上下文，重新写一个吸收了前两轮教训的更精确提示。写提示词的人应该把这条教给用户。

**范围收窄优于反复纠正。** 与其在长提示词里写「不要改 X、不要改 Y、不要改 Z」，不如一开始就把任务切小：只在一个模块里改。小范围的模糊提示，效果好过大范围的高度约束提示。

---

## 5. Few-shot 示例的用法

示例是提示词里性价比最高的部分之一，但有两个常见误用：

- **示例太像玩具**：用 `foo/bar` 之类的假数据，模型学不到真实约束。示例要用真实结构（真实字段名、真实目录层级、真实错误类型）。
- **只给正例**：对于「容易做错的输出格式」，给 1 个正例 + 1 个反例（并说明反例哪里错）比给 3 个正例有效。反例明确划出边界。

格式密集的任务（生成特定 JSON schema、提交信息、变更日志）特别值得配示例；开放式推理任务配示例的收益则低得多，别硬加。

---

## 6. 输出格式的手法

- **用模板而不是形容词。** 「输出要清晰」没用；给出一个带小标题的空模板，模型会照着填。
- **约束长度要小心。** 「控制在 200 字内」有时会让模型丢掉必要信息。更稳的写法是约束**结构**（「用 3 个要点，每点不超过 2 句」）而不是硬性字数。
- **区分「先给什么」和「最终给什么」。** 多阶段任务里明确顺序（先计划、等确认、再实现、最后验证），否则模型会把所有东西混在一段里输出。
- **要求「可复制」而非「可读」。** 交付物是代码/配置时，要求去掉省略号占位、给出完整可运行片段。

---

## 7. 长任务与上下文预算

- **分阶段**：探索 → 计划 → 实施 → 验证。一次跨越阶段，比在一个提示里全塞进去稳。
- **规格外置**：任务复杂时，先让模型产出一份自包含的规格（含涉及文件、接口、明确排除项、端到端验证步骤），再开新会话照着规格执行。干净上下文 + 书面规格 > 带着历史包袱的长对话。
- **善用子代理**：把「读大量文件做调研」丢给独立上下文，主对话只留结论。
- **检查点与回退**：长任务要求分批提交，每批保持可编译可测试，便于回退。注意某些 Agent 的检查点只覆盖文件编辑工具，**不覆盖 Bash 产生的改动**，所以别把检查点当 git 用。

## 8. 反模式对照表

| 反模式 | 症状 | 改用 |
| --- | --- | --- |
| 角色扮演开场白 | 「你是一位资深架构师」占据了开头，但没带来任何行为差异 | 删掉。除非角色能带出具体的判断标准或语气要求 |
| 形容词当标准 | 「高质量、健壮、优雅、可维护」 | 换成可观测指标或反例 |
| 空泛原则清单 | 「遵循最佳实践、注意边界情况、写好注释」 | 删掉，或换成一条具体约定 + 一个范例 |
| 万能收尾 | 「请一步步思考」（对现代推理模型已近乎无操作） | 换成对输出结构的要求 |
| 隐含上下文 | 「改一下那个函数」「按老规矩来」 | 给路径、符号名、可参照的现有实现 |
| 一次多任务 | 一段提示里同时要「修 bug + 加功能 + 补文档」 | 拆成多段/多轮，各自一个目标 |
| 过度规定步骤 | 探索型任务被写成十步死流程 | 改成目标 + 约束 + 对比维度，路径留给模型 |
| 用规则代替验证 | 没写完成定义，只在末尾说「确保正确」 | 给出验证命令和要展示的证据 |
| 问而不给选项 | 追问用户「你要怎么验收」，用户答不上来 | 给出 2~3 个可选项让其挑选 |
| 把源码整段贴进提示词 | 内联几十行代码，占满 Agent 的上下文预算 | 换成文件路径 + 符号名 + 可参照的既有实现；只有报错原文这类无法复现的材料才内联 |

---

## 9. 什么时候不该用提示词

提示词不是万能的。如果用户的需求本质上是「**每次都必须发生、零例外**」的动作，那它属于 hook、脚本或 CI 检查，而不是提示词——提示词是建议性的，模型偶尔会不遵守，而确定性检查不会。同理，如果需求能被一条命令表达，直接写脚本比写提示词可靠。

遇到这种情形，直接告诉用户「这件事更适合写成脚本/hook」，比硬凑一段提示词更有价值。
