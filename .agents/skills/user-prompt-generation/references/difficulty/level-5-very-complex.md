# 难度：复杂（very complex）

## 判据

- 方案本身还没定，需要先调研或设计（找瓶颈、选型、评估迁移路径）。
- 跨多个子系统，或需要长时间连续执行。
- 需要无人值守（CI、批量扇出），或需要多轮 / 多会话协作。

## 提示词骨架

这一级拆成**两段提示词**，而不是一段超长提示词。

### 第一段：探索与设计

```text
背景：<要解决的问题、约束、当前状态>。
已知约束：<性能/兼容/团队能力/时间/依赖限制>。
范围：<允许调研的目录或模块>；本轮只读不写。

任务：给出 <2~3> 个可行方案并对比，而不是直接给一个结论。
对比维度（按重要性排序）：<正确性 / 复杂度 / 可维护性 / 迁移成本 / 性能>。

要求：
- 每个方案说清：核心思路、改动面、风险、以及什么情况下它是最差选择。
- 明确给出你推荐哪个、为什么，以及推荐方案的已知弱点。
- 结论区分「已验证」与「推测」；未验证的标注出来，不要写成笃定的结论。

输出：
1. 现状与关键位置（文件 + 符号）
2. 方案对比表
3. 推荐方案的分阶段实施规格：涉及文件、接口变化、明确排除项、端到端验证步骤
4. 待确认问题清单
```

### 第二段：按规格实施

```text
任务：按下面的规格实施，不要扩大范围。规格里没写到的改动，先问我。

规格：
<把第一段产出的规格原文贴进来>

工作方式：
- 分阶段实施：<阶段一> → <阶段二> → …；每阶段结束跑 <验证命令> 并让我确认，再进入下一阶段。
- 遇到规格没覆盖的情况，不要自行决定：<跳过并记录 / 停下来问我>。
- 每阶段完成后给出改动清单与验证输出，便于回退。

完成定义：<端到端验证步骤> 全部通过；贴出每阶段的实际命令与输出。

输出：阶段进度 → 每阶段改动与验证 → 遗留问题与建议的后续动作。
```

## 为什么要拆两段

把「想清楚」和「做出来」塞进同一段提示词，模型的注意力会被两件事平摊；而且调研阶段读到的几十个文件会把上下文填满，等到动手时，前面那份规格早被挤出去了。规格外置成文本、另起一段（甚至另开会话）执行，比一段长提示词稳得多。干净上下文 + 书面规格 > 带着历史包袱的长对话。

## 无人值守变体

CI、批量修复这类场景用这一级的骨架时，把工作方式换成：

```text
工作方式：逐项处理，每项完成后立即验证；遇到无法自动判定的情况，跳过并记录，不要停下来等确认，也不要强行修改。
```

并把下面三句写进硬性禁止：

```text
硬性禁止：
- 不执行 <破坏性命令>。
- 不修改 <配置文件 / 公共 API>。
- 不为了让检查通过而放宽规则或删测试。
```

要点：无人值守时模型遇到歧义会「自己决定」。所以要提前告诉它**歧义的默认动作是跳过并记录**，而不是猜。

## 裁剪说明

- 不要为了显得完整而把两段合并。这一级宁可多写一段提示词、多开一次会话。
- 第一段的输出格式里强制包含「涉及文件 + 接口变化 + 排除项 + 验证步骤」四项，它才能当规格用。

## 常见坑

- 第一段的产出如果是一篇读着很有道理的调研报告，第二段就没法用。所以规格的四要素要写进输出格式，而不是寄希望于模型自觉。
- 第二段里必须显式写「规格没写到的先问我」。否则模型会把规格当成起点，自行补全它认为合理的设计。
- 这一级的提示词不适合反复微调。同一件事纠正超过两次，说明上下文已被失败方案污染，正确动作是清空重写，而不是继续加规则。
