# 难度：简单（simple）

## 判据

- 改动落在单文件内，或新增一个独立的函数 / 小组件 / 接口分支。
- 方案显然，看一眼代码就知道怎么改，既不需要调研也不需要比较方案。
- 不改公共 API，不引入新依赖。

## 提示词骨架

```text
目标：在 <文件路径> 中 <做什么>，使其 <可判定的终态>。

上下文：
- 技术栈：<语言/框架/版本>，包管理器 <pnpm/npm/...>。
- 相关位置：<文件路径 + 关键符号名>。
- 现状：<现在是什么行为，为什么需要改>。

范围：
- 做：<明确的改动面>。
- 不做：不改动 <无关文件/模块>；不新增依赖；不重排既有代码格式。

完成定义：<命令> 通过 / <可观察行为> 按 <复现方式> 可复现；贴出实际执行结果。

输出：改动的最小 diff + 一句话说明关键决策。

兜底：不确定的 API / 版本 / 路径先查源码或文档，不要凭记忆写。
```

## 裁剪说明

- 可以省掉：实现指引、分阶段、检查点、变量说明。
- 「不做」那一行不能省——它和难度无关，是所有提示词里回报最高的一句。
- 篇幅 15~25 行。

## 常见坑

- 容易只写「目标」不写「现状」。模型不知道现有行为时，可能把你本想保留的行为一起改掉。
- 完成定义别写成「确保正确」或「测试通过」这种口头承诺，写具体命令，或者写一个能观察到的行为。
- 到了这一级仍然不需要 few-shot 示例；示例的收益在格式密集的输出上才明显，常规代码改动靠范例指路（指到仓库里的文件）比给示例划算。
