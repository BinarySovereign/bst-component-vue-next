# 难度：中等（medium）

## 判据

- 单模块内多个文件联动，或新增一个需要对齐既有模式的常规功能。
- 仓库里有可参照的同类实现，方案基本确定，但细节需要模型自己判断。
- 症状清楚、怀疑范围明确的常规 bug 修复也算这一级。

## 提示词骨架

```text
目标：在 <包/模块> 中 <做什么>，使 <可判定的终态>。

上下文：
- 技术栈：<语言/框架/版本>，包管理器 <pnpm/npm/...>。
- 相关位置：<目录 + 入口文件 + 类型定义路径>。
- 现状：<已有实现与数据流，以及为什么现在不行>。

实现指引：
- 参考 <仓库中同类文件路径> 的组织方式、命名与错误处理习惯，保持一致。
- 必须遵守：<本仓库已有的约定，如样式方案、状态管理方式、日志方式>。

范围：
- 做：<交付面>。
- 不做：不改动 <无关模块>；不重构 <既有公共 API>；不新增依赖（除非 <说明门槛>）；不改测试来迁就实现。

测试：本次 <需要 / 不需要> 新增测试。<需要则写明：测试放在 <目录>，参照 <现有测试文件路径>。>

工作方式：动手前先读 <关键文件>，用 3~5 行说明将改哪些文件、按什么顺序，然后直接开始；如果读到的东西推翻了初始判断，先说明再调整。

完成定义：
- <测试命令> 通过；<类型检查 / lint 命令> 无新增报错。
- <关键行为> 按 <复现步骤> 可观察。

输出：改动清单（文件 + 用途）→ 关键代码 → 验证命令与实际输出。

兜底：不确定的 API / 版本 / 路径先查源码或文档确认；被阻塞时说明卡在哪、需要什么。
```

用户选了计划模式时，把「工作方式」那一行换成 `work-modes.md` 里的等待确认版本。

## 裁剪说明

- 「实现指引」是这一级的核心增量。抽象要求（「遵循最佳实践」）没有约束力，指到具体文件才有。
- 默认工作方式是「说明计划后直接开始」。这一级的改动通常还不需要用户逐轮拍板，多问一轮只是拖时间。
- 「测试」那一行不能省。不写要不要加测试，模型大概率顺手写一套，改动面直接翻倍；反过来真要加测试却不给位置和参照文件，它会自成一套写法。
- 篇幅 30~45 行。

## 常见坑

- 模型最容易在这里「顺手抽象」：抽个公共函数、把相似代码合并。要么在「不做」里挡住它，要么明确写出允许哪种抽象、抽到哪里。
- 参照文件给一个就够。给三个，模型会在几种风格之间摇摆，最后混出一个四不像。
- 「现状」别写成「现在有问题」，写清楚当前的数据流和边界在哪，否则模型会重新设计一遍。
