# 工作方式、扫描范围与外部工具片段

这里的每一段都是**拼进成品提示词里的原文**，复制后把 `<>` 换成实际内容即可。

三项各有出处：工作方式来自第 0 步的第 7 项（三选一），扫描范围来自第 2 项（两种写法，全仓扫描和白名单各自都要落进上下文块），外部工具来自第 6 项（需要 / 不需要两种写法）。这三项都是必答输入，漏掉任何一项，前面选的模板再好也会打折。

## 一、工作方式（三选一）

### 怎么选

用户答不上来时按任务特征推，并把推荐和理由一起说给他：

| 任务特征 | 推荐 | 为什么 |
| --- | --- | --- |
| 症状或根因还没定、方案有多个候选、要动的地方跨多文件 | 计划模式 | 计划便宜、改代码贵；先让你看一眼方向再动手，返工代价最小 |
| 只要结论不要改动（找瓶颈、评估方案、摸现状） | 探索模式 | 说清「只读不写」，这份产出才能直接拿去写下一段提示词 |
| 一句话能描述 diff，或用户明确表态要结果不要过程 | 直接开始 | 多一轮确认换不到信息，只是拖时间 |

拿不准就先问一句「这次要的是结论，还是要改完的代码」——这一句能直接分开计划/探索和直接开始。

### 1. 计划模式

适用：方案不确定、改动跨多文件、对涉及代码不熟，或用户明确要求先看计划再动手。

```text
工作方式：先探索、再出计划、等我确认后再动手。
- 先读 <关键文件>，给出 3~6 步实施计划：将改动哪些文件、每个文件改什么、有哪些风险和不确定处。
- 在我回复确认之前，不要修改任何文件。
- 计划里如果发现工作量明显超出预期，先说明，并给出一个更小的替代切分方式。
```

要点：必须显式写「等确认前不改文件」。只说「先给计划」，模型常常会顺手把代码也改了，用户连纠错的机会都没有。

### 2. 探索模式

适用：本轮只要结论——找瓶颈、定方案、评估风险、摸清现状。用户很可能紧接着要拿这份结论去写第二段提示词。

```text
工作方式：本轮只读不写，不要修改任何文件。
- 允许读代码、跑只读命令（查看、搜索、跑测试观察现象）。
- 输出调研结论：现状是什么、关键位置在哪、有哪几条可行路径、各自的代价。
- 结论里区分「我验证过的」与「我推测的」，不确定的标注为未验证。
```

要点：「只读不写」要在同一句里把边界画出来（可以读、可以跑观察性命令、不可以改文件），否则模型会把「不要修改」理解成「不要用 Bash」。

### 3. 直接开始

适用：一句话能描述改动，或用户已经明确表态要结果不要过程。

```text
工作方式：直接动手，不要先出计划。
- 边改边用一句话说明关键决策；遇到需要我在多个方案里选的时候再停下来问。
- 完成后一次性给出改动清单与验证结果。
```

要点：直接开始不等于不做验证。把「完成后给验证结果」留在里面，否则模型会在「已完成」三个字上停住。

## 二、扫描范围（两种写法）

### 4. 扫描整个项目

适用：改动位置不明确，或需要 Agent 自己在全仓定位。

```text
上下文：涉及位置尚未完全确定，请自行在仓库中检索定位。
- 优先看 <顶层目录/包>；检索手段：搜索符号 <符号名>、文件模式 <pattern>。
- 定位到之后，先说明你选中的文件与理由，再动手。
```

要点：给检索线索（符号名、文件模式、疑似目录）比只写一句「你去找找」有效得多——后者容易让模型读几十个无关文件，把上下文预算烧光。

### 5. 指定目录（白名单）

适用：用户已明确范围，或这是本次降低跑偏概率的主要手段。

```text
上下文：相关代码只在以下目录，无需遍历整个仓库：
- <目录一>
- <目录二>

范围：只允许改动上述目录内的文件；确有必要越界时，先说明理由并等我确认。
```

要点：白名单要同时约束「读」和「改」。只写「只看这几个目录」而不限制改动范围，模型仍然会顺手改到外面去。

## 三、外部工具（两种写法）

### 6. 需要调用工具

适用：第 6 项答「是」。工具名从用户那里逐个确认，不要用「联网工具」「文档工具」这类泛称。

```text
可用工具：本次允许调用 <工具名 A>、<工具名 B>。
- 只在需要 <用途> 时调用，不要用它们做别的事。
- 不要调用上面没列出的工具；如果你的思路依赖某个没列出的工具，先说明再等我确认。
- 工具返回结果与我的描述或仓库现状冲突时，以工具返回为准，并指出冲突点。
- 工具不可用、或调用后查不到时，直接说明「查不到」，不要退回到凭记忆给答案。
```

要点：这一段的价值几乎全在最后两句。工具存在的意义就是替代记忆，如果不写「查不到就说查不到」，模型会在工具返回空结果后自己补一个看起来很合理的版本号或 API 签名——比不调工具还危险，因为你会以为它查过了。

两处落笔细节：**工具名用 `{{工具名}}` 变量占位**，方便用户按自己的环境替换，但不要用「联网工具」「文档工具」这类泛称顶替变量——泛称等于把「该用哪个工具」重新推回给模型猜。另外，这一段已经把工具相关的兜底写全了，成品末尾的兜底块不必再重复一遍「查不到就说查不到」；同一条约束写两处只会稀释注意力。

### 7. 不需要工具（但在提示词里表态）

适用：第 6 项答「否」，但任务沾到下面四类信息中的任何一类——**版本号 / 兼容性 / 报错的通用原因与解法 / 第三方库的用法与行为**。纯本地的小改（改文案、调样式、单文件逻辑）不用写这一段。

判断时直接对着提示词扫这几个词根：**最新 / 版本 / 兼容 / 报错原因 / 第三方怎么用**。扫到任何一个就补，扫不到就跳过——比凭「它听起来像不像个本地问题」可靠。调试类任务几乎必然命中第三类，别因为「看着是个本地 bug」就跳过。

```text
本次不需要联网或外部工具，只用仓库内已有手段完成。
- 版本号看 lock 文件与 package.json；API 行为读仓库内源码或本地依赖的类型定义。
- 拿不准就说明拿不准，不要凭记忆补一个看起来很合理的答案。
```

要点：这一段不是在禁止工具，而是在**给模型一个不联网也能走的路径**。只说「不许联网」，模型会在信息不足时硬编；告诉它去哪儿找依据，它才真的不编。

## 四、和难度模板的配合

难度模板里的「工作方式」块是占位文字，实际写的时候用上面第 1~3 段的对应原文替换掉。低难度和超简单难度要压缩，见各难度模板的裁剪说明。

低难度配计划模式、高难度配直接开始，都属于用户有权做的选择，但值得提一句代价：

- 超简单 / 简单 × 计划模式：多一轮交互，换不到任何有用信息。
- 较复杂 / 复杂 × 直接开始：一次改得太大，出问题时没有可回退的中间点。这时至少在提示词里保留「分批实施 + 每批跑验证」。
