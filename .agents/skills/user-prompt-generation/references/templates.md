# 场景模板库

按任务类型取用。模板里的 `<>` 是必填槽位，`[ ]` 是可选槽位；骨架可整段改用，但**别删掉「范围中的不做什么」「完成定义」「输出格式」这三块**——它们是最常被省略、也最影响结果质量的部分。

本文件只负责「这一类任务该问哪些细节」。骨架的篇幅、分不分阶段、要不要先出计划，由难度决定，见 `difficulty/` 下的五份模板；两种骨架配合使用，对不上时流程听难度的、细节听这里的。工作方式、扫描范围与外部工具的片段在 `work-modes.md`。

---

## 1. 新建功能（Agent 有仓库读写权限）

适用：从零实现一个模块/组件/接口，代码库已存在。

```text
目标：在 <仓库/包> 中新增 <功能名>，使其 <可判定的终态>。

上下文：
- 技术栈：<语言/框架/版本>，包管理器 <pnpm/npm/...>。
- 相关位置：<目录路径>；入口文件 <路径>；类型定义 <路径>。
- 现状：<已有实现或数据流的简述>。

实现指引：
- 参考 <某现有文件/组件> 的组织方式与命名习惯，保持一致。
- 必须遵守：<已有的约定，如错误处理方式、状态管理方式、样式方案>。
- 依赖：仅使用仓库已有依赖，<是否允许新增，允许则说明理由门槛>。

范围：
- 做：<明确的交付面>。
- 不做：不改动 <无关模块>；不重构 <既有公共 API>；不改测试来迁就实现。

工作方式：
- 动手前先读 <关键文件> 并给出 3~6 步实施计划，说明将改动哪些文件；我确认后再写代码。

完成定义：
- <命令> 通过；<命令> 无新增报错。
- <可观察行为> 可复现。

输出格式：
1. 实施计划（先给，等我确认）
2. 改动文件清单与每个文件的用途
3. 关键代码
4. 验证：贴出执行过的命令与实际输出

兜底：不确定的 API / 版本 / 路径先去源码或文档确认，不要凭记忆写；被阻塞时说明卡点与需要的信息。
```

要点：新建功能最容易出的问题是「顺手引入新依赖」和「顺手重构周边」，所以「不做什么」和「依赖门槛」必须写清。计划确认这一步在跨文件任务上回报极高。

## 2. 精准小改（范围越窄越好）

适用：改文案、改样式、调参数、补一行逻辑——一句话能描述 diff 的改动。

```text
目标：<一处精确改动>，位置 <文件路径:行号或符号名>。

约束：只改这一处；不要重排格式、不要顺手优化周边代码。

完成后：<验证方式，如「说明改动前后行为差异」或「跑 <命令>」>。

输出：只给改动的最小 diff。
```

要点：小改的提示词要**短**。给它加十条通用规范只会稀释焦点。这里「不要顺手优化」比任何正面要求都重要。

## 3. 调试 / 修复 bug

适用：有明确报错或异常行为。

````text
问题：<用户可观察到的症状>。
复现：<步骤 / 输入 / 触发条件>。
报错：
```text
<完整的错误栈或日志原文>
```
环境：<版本、平台、最近改动>。
怀疑区域：<目录或模块>（仅供起点，不排除在别处）。

任务：
1. 先定位根因，说明它是如何导致上述症状的；给出证据（日志、代码路径、复现）。
2. 写完根因分析后再修复。修根因，不要靠 try/except 或放宽校验把错误压下去。
3. 如果同类模式在别处也有，列出来但不要顺手全改。

完成定义：
- <复现命令/测试> 从失败变为通过。
- 贴出修改前后的实际输出。

输出：根因 → 修改 → 验证证据，三段式。
````

要点：调试提示词里「修根因、不许抑制错误」比什么都重要，否则模型很容易用兜底逻辑把症状藏掉。报错原文务必内联——这是少数必须内联、不能靠 Agent 自取的材料。

## 4. 重构 / 迁移

适用：行为不变的前提下调整结构，或从 A 库迁到 B 库。

```text
目标：把 <范围> 从 <现状> 调整为 <目标结构>，<外部可观察行为必须保持不变 / 或列出允许变化的部分>。

约束：
- 不改变对外 API：<函数签名 / 导出 / 组件 props 清单>。
- 保持既有测试全绿；测试若需调整，只允许改内部断言，不得放宽断言强度。
- 一次性完成，不留 <临时兼容层 / TODO>。

步骤：
1. 先列出所有受影响的位置（文件 + 符号）与调用方，我确认范围后再动手。
2. 分批提交，每批保持可编译、测试可过。

完成定义：<测试命令> 全绿；<类型检查命令> 无错；对外行为 diff 为空（附对比方式）。

输出：影响面清单 → 分批改动 → 每批验证结果。
```

要点：重构最大的风险是「静默的行为漂移」。用「对外行为不变 + 测试不得放宽断言」把它钉死，并要求先给影响面清单。

## 5. 代码审查 / 评审

适用：审一段 diff、一个 PR、一个模块。

```text
审查对象：<PR 链接 / diff / 文件路径>。
审查目标：只标记影响 <正确性 / 明确需求> 的缺口，其余一律作为可选建议，标注清楚。

请按此结构输出：
1. 阻断性问题（必须改）：每条给出「位置 + 问题 + 为何有问题 + 建议」。
2. 建议性问题：同上，但标明「可选」。
3. 需要作者确认的疑点：<边界情况 / 隐含假设>。

约束：
- 每条结论必须能指回代码中的具体位置，不要给泛泛的风格评论。
- 不要为了凑数而报告问题；找不到阻断性问题就直接说没有。
- 不要提出超出本次改动范围的架构建议。
```

要点：审查提示词如果不加「只报影响正确性的问题」，模型会稳定地报出一堆无关紧要的发现，导致过度工程。明确「可以说什么都不报」很关键。

## 6. 补测试

适用：为现有代码补单元/集成测试。

```text
目标：为 <文件/组件路径> 补测试，覆盖 <需要覆盖的行为清单>。

约定：
- 沿用仓库现有测试栈与写法，参考 <现有测试文件路径>。
- 测试放在 <目录规则>，文件命名 <规则>。

覆盖要求：
- 必须覆盖：<边界值 / 错误路径 / 状态转换 / 并发或时序>。
- 不要用 mock 掩盖被测逻辑；<明确哪些依赖可以 mock>。
- 每个用例名要能说明在被测行为，不写 test1 / should work。

范围：只新增测试，不修改被测源码来迁就测试；若发现源码有 bug，单独指出，不要顺手修。

完成定义：<测试命令> 全绿，并说明每个用例验证的行为。

输出：测试文件 + 运行结果 + 未覆盖到的行为（如有）说明。
```

要点：「不修改被测源码来迁就测试」是必须写的一条，否则模型很可能为了让测试通过而改实现。反过来，发现真 bug 时要求它「单独指出」而不是顺手修。

## 7. 方案设计 / 技术选型（探路型）

适用：还没有确定方案，需要先调研比较。

```text
背景：<要解决的问题、约束、当前状态>。
已知约束：<性能/兼容/团队能力/时间/依赖限制>。

任务：给出 2~3 个可行方案并对比，而不是直接给一个结论。

对比维度（按重要性排序）：<正确性 / 复杂度 / 可维护性 / 迁移成本 / 性能>。

要求：
- 每个方案说清：核心思路、改动面、风险、以及「什么情况下它会是最差选择」。
- 明确给出你推荐哪个、为什么，以及推荐方案的已知弱点。
- 不确定的地方标注「未验证」，不要给出看起来笃定的结论。

范围：本轮只出方案，不写实现代码。

输出：方案对比表 + 推荐及理由 + 待确认问题清单。
```

要点：探路型任务的提示词要给**对比维度**和**反方视角**（「什么情况下它最差」），否则模型倾向于给一个四平八稳的万能答案。明确「本轮不写代码」避免它跑偏去实现。

## 8. 无人值守 / 批量任务（Agent）

适用：CI、批量修复、按文件扇出、不给人工确认的机会。

```text
任务：<可机械判定成功与否的批量目标，如「修复所有 lint 错误」>。
范围：限定在 <路径/文件清单>；不得跨出该范围。

工作方式：
- 逐项处理，每项完成后立即验证；不要在所有改动做完后才统一验证。
- 遇到无法自动判定的情况，跳过并记录下来，不要停下来等待确认，也不要强行修改。

硬性禁止：
- 不执行 <破坏性命令>；不修改 <配置文件 / 公共 API>；不新增依赖。
- 不为了让检查通过而放宽规则或删测试。

完成定义：<命令> 无错误；贴出命令与输出。

输出：处理清单（已改/跳过/原因）+ 验证结果 + 遗留问题。
```

要点：无人值守场景下，模型遇到歧义会「自己决定」。所以要提前告诉它**歧义的默认动作是跳过并记录**，而不是猜。同时收窄工具与路径权限。

---

> 本文件只覆盖**编码 Agent** 场景。只能对话、读不到仓库的网页端模型不在覆盖范围内——第 0 步的「扫描范围」和「工作方式」两项在那种场景下都没有可填的值。
