# 用户提示词生成

## 这个 skill 治的是什么病

让 AI「写一个提示词」，最常见的产出不是坏提示词，而是**看起来像提示词的废话**：开头一句「你是一位拥有十年经验的资深架构师」，中间一堆「请遵循最佳实践、保证代码质量、注重可维护性」，结尾「让我们一步步思考」。这段文本读起来很专业，实际对模型几乎没有约束力——因为里面没有任何一个词能告诉模型「做到什么程度算对」。

第二类高频失效是**不问就写**：AI 自己脑补了技术栈、难度等级、目录结构、版本号，甚至脑补了一个根本不存在的工具名，用户拿到一段漂亮但跟自己项目对不上的提示词，只能全部重来。

第三类失效是把提示词写成**操作手册**：每一步都写死，模型只能照做，碰到没写到的分支就卡住或瞎猜。提示词的长度不是质量指标，**能被验证的约束才是**。

所以本 skill 的核心纪律只有三条：

1. **先问齐七项输入，再动笔。** 缺必填项就先问，不要自己编。
2. **每一句都必须可判定。** 写完后逐句问「模型怎么知道自己做到了这一条」，答不上来的就重写或删掉。
3. **交付的是给机器执行的指令，不是给用户看的文案。** 不为了显得专业而堆形容词。

## 第 0 步：按顺序确认七项输入

这七项是本次提示词的输入参数，顺序不要打乱：先定难度、扫描范围和可用工具（决定骨架、上下文形态和模型的行动边界），再定语言、目标和参考指引（决定交付物长什么样），最后定工作方式（决定模型怎么干活）。写之前七项都要有落点，只有第 5 项可以空着过去。

| # | 要确认的 | 必填 | 它决定什么 |
| --- | --- | --- | --- |
| 1 | **任务难度等级**：超简单 / 简单 / 中等 / 较复杂 / 复杂 | 是 | 用哪份难度模板（`references/difficulty/`）、提示词该多长、要不要强制先出计划 |
| 2 | **扫描范围**：是否需要扫描整个项目；若否，具体是哪几个目录 | 是 | 上下文块写成「Agent 自行在全仓定位」还是「目录白名单 + 禁止越界」 |
| 3 | **提示词语言**：中文 / 英语 | 是 | 交付文本用什么语言写。选错整段都要重做 |
| 4 | **本次目标**：这次任务要完成什么 | 是 | 目标块。同时要顺手把不可判定的表述改成可判定 |
| 5 | **参考指引或范例**：代码、文档、规范、既有实现 | 否 | 实现指引块。有就指过去，没有就用「仓库中同类实现」占位 |
| 6 | **外部工具**：是否需要调用 MCP 工具、联网搜索工具等（不限于这两类）；若需要，是哪些（逐个列出工具名） | 是 | 提示词里要不要写「可用工具」块，以及防编造条款怎么写 |
| 7 | **工作方式**：计划模式 / 探索模式 / 直接开始 | 是 | 工作方式块。模型是先出计划等确认、只读不写、还是直接改文件 |

### 怎么问

- 优先用环境里现成的结构化提问工具（例如 `ask_followup_question`）把七项一次性抛出，每项带上预设选项。用户点选比打字快，也不容易滑向「随便都行」；反过来，把七项拆成七轮对话会把耐心磨光。
- 没有结构化提问工具时按序号分条问，一次最多三条，先问最影响结果的那几项（难度、扫描范围、工作方式、外部工具）。
- **必填不等于必须逐字问。** 用户在这轮对话里已经交代过的（「用 vitest 补测试」「只改 `packages/components`」「可以用联网搜索」），复述一句确认就够，不要重复盘问。
- 用户答不上来的项（难度和工作方式最容易卡住），给 2~3 个选项加一句你的推荐与理由。追问「你觉得呢」通常只会换来一句「你看着办」。
- 六项必填没有落点之前不要动笔。猜错难度的代价尤其大——它会连带错掉模板、篇幅和整个工作流程。

### 逐项细则

- **难度**：不要只让用户自评。给他判据，或者让他用一句话描述这次改动（改哪里、改几个地方、会不会碰到别人依赖的东西），由你定级并复述理由。完整判据与常见误判见 `references/selection.md`。
- **扫描范围**：选「否」时必须落到具体目录集合，不能停在「相关部门」这种说法上；用户说不出来，就从任务描述里推 2~3 个候选目录让他确认。范围最终要能以目录白名单的形式写进提示词，并且同时限制「读」和「改」。
- **语言**：可以和用户当前对话语言一致，但仍然要确认一次。交付语言写错，整段都要返工。
- **目标**：用户给的原始目标里如果带着「优化 / 完善 / 提升 / 重构一下」这类词，复述时直接换成可判定表述，并在交付时说明你改写过哪里。
- **参考指引**：没有不必等，用「参考仓库中 `<同类实现路径>`」占位，并提醒一句「补上具体文件路径能让产出更贴你的手法」。缺这一项不构成停下来的理由。材料与任务类型不匹配时（比如拿一份通用开发规范去修一个 bug），指到相关章节并显式排除无关条款——不排除，一次小修很容易被扩成一次全仓规范整改。
- **外部工具**：先问要不要用，再问用哪些。工具名要一个一个确认清楚——这是七项里唯一必须落到具体名称的一项，因为模型最常编的就是工具名和参数。用户只给泛称（「有个查文档的工具，叫什么我忘了」）时要追问到具体名称；追问不到就在交付里留变量占位，不要替他猜一个。
  - **答「是」** → 写「可用工具」块，工具名逐个列出。交付时工具名用 `{{变量}}` 占位，方便用户按自己的环境替换；但**不要用「联网工具」「文档工具」这类泛称顶替变量**，泛称等于把「该用哪个工具」重新交回给模型猜。
  - **答「否」** → 通常不用在提示词里表态。但任务只要沾到下面四类信息中的任何一类，就补一句「本次不需要联网或外部工具」：
    1. 某个包的版本号、最新版、升级路径；
    2. 兼容性（浏览器 / Node / 框架大版本）；
    3. 某个报错的通用原因与解法——**调试类任务几乎都落在这一类，最容易漏**；
    4. 第三方库的用法、配置或行为。
    判断时直接对着提示词扫这几个词根：**最新 / 版本 / 兼容 / 报错原因 / 第三方怎么用**。扫到就补，扫不到就跳过，比凭「感觉它会不会联网」可靠。
  - 不管哪种答案，都顺带说明工具不可用时怎么办，否则它会退回到凭记忆编。
- **工作方式**：计划模式 = 先给计划、等确认、期间不动文件；探索模式 = 只读不写，本轮只出调研结论或方案；直接开始 = 直接改文件，边做边说明关键决策。

顺带推出来的两件事，不用单独问，但写之前心里要清楚：

- **执行者是谁。** 本 skill 只覆盖能读仓库、能跑命令的编码 Agent（Claude Code / CodeBuddy / Cursor 这类）——第 2 项「扫描范围」和第 7 项「工作方式」能成立，前提就是执行者能自己扫仓库、能自己改文件、能自己调工具。用户如果说是要发给只能对话的网页端模型，这些项都没有可填的值，这套流程也就不适用了：直接说明「不在覆盖范围内」，别硬套一套它执行不了的提示词。
- **硬约束和完成的定义。** 从第 4 项（目标）和第 5 项（参考指引）里挤出来，必要时补问一句：有哪些不能动的东西、跑哪条命令算做完。

### 难度和工作方式打架时

这两项会互相矛盾：超简单 × 计划模式是白白多等一轮，复杂 × 直接开始容易一次改得太大回不了头。发现矛盾就提一句你的建议和背后的代价，然后**仍然按用户的选择写**。选择权在用户手里，你的职责是把代价说清楚，不是替他决定。

## 第 1 步：综合判断选模板

骨架是两层拼出来的：**难度定流程，任务类型定内容。**

先按难度取模板，一份就够，不要混着抄：

| 难度 | 模板 | 骨架特征 |
| --- | --- | --- |
| 超简单 | `references/difficulty/level-1-trivial.md` | 10 行以内，只留目标、范围、验证、输出 |
| 简单 | `references/difficulty/level-2-simple.md` | 15~25 行，补上上下文与完成定义 |
| 中等 | `references/difficulty/level-3-medium.md` | 30~45 行，补上实现指引与简短计划 |
| 较复杂 | `references/difficulty/level-4-complex.md` | 影响面清单 → 确认 → 分批实施 → 每批验证 |
| 复杂 | `references/difficulty/level-5-very-complex.md` | 拆两段：调研出规格，再照规格执行 |

每个难度模板里都写了判据、可直接填空的骨架、该裁剪掉哪些块、以及这个级别特有的坑。

再按任务类型补内容重点：`references/templates.md` 里是八类场景骨架（新建功能、精准小改、调试、重构迁移、代码审查、补测试、方案设计、无人值守）。两者的分工很清楚：

- **难度模板给流程与篇幅**：简单级不分阶段，复杂级必须分批、必须等确认。
- **场景模板给这一类任务特有的要求**：补测试必须写「不修改被测源码来迁就测试」，代码审查必须写「找不到阻断性问题就直接说没有」，无人值守必须写「歧义的默认动作是跳过并记录」。
- **两者对不上时**（比如「复杂的调试」），**流程听难度的，细节听场景的**。

最后把工作方式、扫描范围和外部工具贴进去：`references/work-modes.md` 里有「计划模式 / 探索模式 / 直接开始」三段可粘贴原文、「全仓扫描 / 目录白名单」两种写法，以及「需要工具 / 不需要工具」两种写法。贴的时候有四件事要注意：

- **片段按难度压缩。** 那些原文是按中等以上难度写的。到了超简单和简单级别，工作方式和范围各压成一行就够（「直接动手，不要先出计划」／「只改 `<路径>` 这一处」），整段搬会把篇幅上限撑爆，焦点也跟着散掉。
- **白名单要拆成两半。** 能读的范围进「上下文」块，能改的范围进「范围」块。只限读不限改，模型照样会改到白名单外面去。
- **复杂级别配探索模式时，只交付两段里的第一段。** 明确告诉用户「这一段只负责拿到根因与规格，实施提示词等规格出来再生成」，并说明第二段从哪里来。把两段塞进一次交付，用户拿到的那段自己也验收不了。
- **工具名要逐个列出，并写死边界。** 「需要查一下最新版本」这种说法没有约束力；写成「允许调用 `<工具名 A>`、`<工具名 B>`；不要调用未列出的工具」，模型才不会去猜一个不存在的工具。交付时工具名用 `{{变量}}` 占位（方便按环境替换），但不要退化成「联网工具」这类泛称。再把「查不到就说明查不到，不要凭记忆给答案」并进去——工具存在的意义就是替代记忆，不写这句等于白配；写了之后，末尾的兜底块就不用再重复一遍。

## 第 2 步：写，而不是套

结构有了，内容质量取决于下面这几条判断：

- **用「为什么」驱动约束，而不是堆大写的 MUST / NEVER。** 模型对「解释清楚原因的约束」遵守得更好；满屏 MUST 会让所有约束一起贬值，包括真正重要的那条。
- **具体压倒抽象。** 给数字、给路径、给范例、给反例。「响应要快」没有信息量，「单次请求 < 200ms，且不新增同步 IO」才有。
- **一个提示词一个目标。** 把互不相关的任务塞进一段，会让模型的注意力平摊，通常两件事都做差。该拆就拆。
- **规则数量和遵守率成反比。** 只留「删掉它模型就会做错」的规则。判据就是逐条自问：删掉这条，输出会变差吗？不会就删。
- **别替模型把步骤写死。** 任务是探索性的（「找出性能瓶颈」「评估这个方案」）时，留出「先看再定」的空间比给出五步流程更有用。反过来，步骤确定、易错的机械操作，才值得写死。
- **防编造要显式写。** 编码 Agent 最容易编的就是 API 签名、库版本、文件路径、工具名。一句话「不确定的 API 先查源码或文档确认，不要凭记忆写；工具查不到就说查不到」能省掉大量返工。

## 第 3 步：交付前自检

逐条过，任何一条不合格就回去改，不要带着问题交付。

| 检查项 | 不合格的样子 | 怎么改 |
| --- | --- | --- |
| 目标动词可判定吗 | 「优化 / 完善 / 提升质量 / 重构一下」 | 换成有指标、有边界、有终态的表述 |
| 有完成定义与验证方式吗 | 只说「实现 X」，没说怎么算对 | 补「跑 `pnpm test x` 通过 / Y 行为可观察」 |
| 有输出格式吗 | 没有 | 会收到形状随机的回答；用模板或字段列表固定 |
| 写了「不要做什么」吗 | 没有 | 补一条：不改无关文件 / 不加新依赖 / 不改公共 API |
| 提到代码时给的是路径/范例吗 | 「改一下那个函数」「那个组件」 | 换成具体路径或可参照的现有实现 |
| 上下文给的是线索还是全文 | 把组件源码整段贴进提示词 | 执行者能自己读仓库，换成文件路径 + 符号名；只有报错原文这类无法复现的材料才内联 |
| 说了要用工具却只写了用途 | 「可以用联网工具查一下最新版本」 | 列出具体工具名，并补「不要调用未列出的工具 / 查不到就说查不到」 |
| 答「否」却没表态 | 任务要查版本、兼容性、报错原因或第三方库行为，提示词里却没提一句不联网 | 补「本次不需要联网或外部工具，只用仓库内已有手段」，并告诉它去哪儿找依据 |
| 难度和工作方式匹配吗 | 超简单的改动却配了一段「先出实施计划、等我确认」 | 降级模板或改直接开始；小改动先给计划纯属浪费轮次 |
| 扫描范围落进上下文块了吗 | 说了只改某目录，提示词里却没有白名单 | 补「只允许改动 `<目录>`，确需越界先说明理由」 |
| 有形容词冒充标准吗 | 「健壮 / 优雅 / 高质量 / 可维护」 | 换成可观测指标或明确的反例 |
| 有无与任务无关的规则 | 把通用的编码规范整段搬进来 | 删掉；每条冗余规则都在稀释其他规则 |
| 步骤是否写得太死 | 探索型任务给了十步死流程 | 改成目标 + 约束，把路径留给模型 |
| 语言确认了吗 | 没确认就动笔 | 先问 |
| 是否可能诱导编造 | 没提「不确定就查」 | 补兜底条款，工具类任务补「查不到就说查不到」 |

## 第 4 步：交付格式

固定用下面这个结构交付，让用户一眼能复制、能判断、能追问：

````markdown
（一句话）这段提示词面向 <执行者>，用于 <任务>。

### 前置说明

只写适用的那几行，不适用的不要凑数：

- 选型：难度 <等级> × 工作方式 <模式> → 用的是 <哪份模板>，裁掉了 <哪些块>。
- 由我判定：<用户弃权、由你替他定的难度 / 工作方式 / 扫描范围 / 工具，以及依据>。
- 目标改写：<把用户原话里的不可判定表述改成了什么>。
- 代价提示：<难度和工作方式冲突带来的代价，以及更稳的替代做法>。

### 提示词

```text
<可直接复制的成品。需要用户自己替换的地方，用 {{变量名}} 标出。>
```

### 变量说明（如有）

- `{{变量名}}`：是什么、怎么填。

### 设计要点

- 2~4 条关键取舍，重点说清「看起来可以更简单，但为了 X 故意这么写」的地方。

### 可选加强

- 想更强控制可以加：<更硬的约束 / few-shot 示例 / 验证脚本 / 分阶段工作流>，并说明各自的代价。
````

「前置说明」这几行是给用户复核用的：他把难度、工作方式、你替他做的决定、你改写过的目标一次看全，定错了可以直接让你重来；没有这几行，他只能凭感觉判断整段提示词是不是合身。不适用的行不要凑数——没有冲突就不写代价提示，没有弃权就不写由我判定。

「由我判定」和「目标改写」都要求给出依据，不是只报结论：「改了 3 个文件但没动对外签名，我放中等」「原文『老是有问题』没法验收，改成了两条可观察的行为」。给了依据，用户才有机会反驳；只给结论，他只能接受一个不知道从哪来的判断。

## 第 5 步：被反馈「没效果」时的迭代

用户回来说「试了没用」，先问**具体失效现象**，别盲目加规则。不同症状对应不同修法：

- **答非所问**：多半是目标和输出格式没写清 → 回去改第 1 步拼出来的「目标」与「输出格式」两块。
- **范围失控**（改了不该改的、加了依赖）：缺「不做什么」或既有约定没给 → 补范围与范例，检查扫描范围有没有写成白名单。
- **编造 API / 版本 / 路径 / 工具名**：缺兜底条款，或上下文没给够 → 补「不确定就查」，工具类任务检查有没有逐个列出工具名。
- **做了一半就宣称完成**：缺完成定义与证据要求 → 补验证命令与「展示证据」。
- **大任务中途跑偏**：单轮承载过多 → 拆成分阶段/多轮，或引入计划确认再执行。
- **模型做少了或做多了**：难度定级偏了 → 换高/低一级的难度模板重写，而不是在原提示词上继续堆规则。加规则治不了定级错误。

改完后重新过一遍第 3 步自检，再交付。
