# Dependency Selection

## 这个 skill 治的是什么病

选版本这件事上，AI 最常见的失效模式不是算错，而是**跳过查询、凭记忆回答**。记忆里的 "latest" 通常落后几个月，而依赖选择恰恰是那种过期一个月就出错的活儿。第二常见的失效是**凭版本号推测兼容性**——认为主版本相同就兼容、主版本不同就不兼容，这两种推测都经常不成立。

所以本 skill 的核心纪律只有一条：**每一个出现在推荐里的版本号，都必须能指回某条命令的实际输出**。做不到这一点时，宁可明说「未验证」，也不要给出看起来笃定的答案。

还有一种失效更隐蔽：**只看技术约束，不看包本身的生态位**。一个包可以完美通过 engines、peer、联动簇的所有检查，却依然是坏选择——只要它几乎没人用。周下载量几百的包通常意味着维护者已弃坑、issue 无人应答、下一个大版本可能永远不会来；引入它，等于把一份卖不掉的供应链风险写进 lockfile。下载量是这类问题里最便宜、最可量化的探针，所以本 skill 把它当成一道**硬门槛**，而不是一句「仅供参考」的风险提示。

## 工作流程

### 第 1 步：采集候选版本（不可跳过）

先查「有什么可选」，再谈「该选什么」。跳过这一步直接给建议，等于在猜。

| 目的 | 命令 |
| --- | --- |
| 看版本标签分布 | `pnpm view <pkg> dist-tags --json` |
| 看全量版本列表 | `pnpm view <pkg> versions --json` |
| 看候选的硬约束 | `pnpm view <pkg>@<ver> engines peerDependencies peerDependenciesMeta --json` |
| 看发布与废弃情况 | `pnpm view <pkg>@<ver> deprecated time.modified --json` |
| 看下载量（包级门槛） | `node <skill-dir>/scripts/downloads.js <pkg> [<pkg>...]` |
| 看下载量（单包直查） | `curl -s https://api.npmjs.org/downloads/point/last-week/<pkg>` |
| 看当前落后多少 | `pnpm outdated -r` |
| 看实际解析结果 | `pnpm why <pkg> -r` |
| 看本仓库版本约定 | 读 `pnpm-workspace.yaml` 的 `catalogs` 段 |

`dist-tags` 尤其值得细看：它除了 `latest`，常带有历史大版本线标签（如 `V4`）和 `previous`。这些标签能直接告诉你「某个大版本线的最后一个稳定版是哪个」，比在 `versions` 里肉眼翻找可靠得多。

单独看 `latest` 是危险的：它可能刚发布几小时、可能有已知回归，而 `previous` 才是上一个稳定线。给出建议时要说明你倾向哪条线以及理由。

### 第 2 步：先过包级门槛，再筛版本

两类筛选的成本和后果完全不同：**包级门槛**决定「这个包值不值得进入讨论」，**版本级约束**决定「它的某个版本能不能装进这个仓库」。包级门槛要放在前面——如果连包本身都不该用，那么仔细比对它的版本，只是在为一堆垃圾工作做精装修。

#### 2.1 下载量门槛（包级硬排除）

下载量同时代理了三件事：维护活跃度、issue 响应速度、长期存续概率。它不能证明一个包好，但能可靠地告诉我们一个包**几乎没人在用**，而后者已经足够构成排除理由。

以最新一周（`last-week`）的量级为准：

| 周下载量 | 判定 | 处理方式 |
| --- | --- | --- |
| < 10,000 | **排除** | 不进入版本对比，直接剔除。若用户的目标确实只能由它实现，改为「寻找替代」：给出 2–3 个量级更高的候选，并说明取舍 |
| 10,000 ~ 100,000 | **灰区** | 可以采纳，但必须在「依据」里写出真实数值，并说明为什么没有更主流的替代 |
| ≥ 100,000 | 放行 | 正常进入版本级筛选 |

10,000 是**默认值，不是教条**。当候选是某个生态里唯一能用的工具，或仓库本来就依赖一批小众包时，用 `--min <n>` 调低门槛并写明理由，比硬套数字更有用。反过来，给核心构建链选包时把门槛上调也合理——这取决于引入的包失败时会有多痛。

**这道门槛管「要不要引入」，不管「要不要升级」。** 已经在 `package.json` 里的包不适用硬排除：你已经在用它了，因为下载量低而拒绝升级，只会让你同时承受「旧版本」和「小众包」两份代价。这种情况把低下载量写成**长期维护风险**并建议评估替代，但版本建议照常给。

以下几类天然没有公开下载量，跳过这道门槛，并把跳过的理由写进「未验证项」：

- 通过 `workspace:` 协议引用的仓内包
- 私有 registry / 企业内部包
- 在 npm 上根本不存在的名字——这对一个**准备新引入**的包是最硬的排除信号，通常是拼写错误，或者是仿冒包

#### 2.2 版本级约束

逐条过，每条都可能直接淘汰候选：

1. **引擎约束** —— 比对 `engines.node` 与仓库 `package.json` 的 `engines` 声明。注意 `">=20"` 这类宽松写法包含 `20.0.0`，而很多包要求 `^20.19.0`，看似兼容实则不然。这类冲突属于「要先改前提」，要单独指出来，不能混在升级动作里。
2. **peer 依赖** —— 读候选的 `peerDependencies` 与 `peerDependenciesMeta`，逐条比对仓库现有版本。**不要用主版本号推测兼容性**：peer 区间经常横跨多个主版本（例如同时接受 `^6 || ^7 || ^8`），也经常拒绝同主版本的某些区间。
3. **联动簇** —— 存在必须同进同退的包组：Vue 生态的 `vue` 与 `@vue/server-renderer`；测试侧 `vitest` / `@vitest/ui` / `@vitest/coverage-v8`（peer 常要求精确同版本）；lint 侧的 `eslint` / `@eslint/js` / `@typescript-eslint/*`。只动其中一个是常见错误，检查 peer 声明来确认簇的边界。
4. **分组归属** —— 在 pnpm catalog 仓库里，候选要能落进某个既有分组；落不进去说明它可能属于新用途，需要先问「为什么它要单独成组」，而不是随手加一行。
5. **预发布版本** —— `alpha` / `beta` / `rc` / `next` 默认剔除。除非用户明确要试，否则不要把它们写进建议。

### 第 3 步：判定，而不是直接给结论

被包级门槛拦下的包不到这里，它们的判定就是「排除」。走到这一步的候选，只有四种判定，必须显式标注，因为它们的行动成本完全不同：

- **排除**：包本身不该用（下载量过低、npm 上不存在、或已明确无人维护）。要给出排除所依据的数值，并指出替代方向。
- **放行**：满足全部约束，可以直接采纳。说明它是否跨主版本，以及跨版本时的破坏性变更。
- **冲突**：需要连带改其他包才能成立（例如新版本把 `@types/node` 下限顶到 22，而仓库锁在 20）。要列出完整连带链，并给出「连带改动清单」。
- **阻止**：被更上游的前提挡住（例如要求 Node 版本高于仓库声明）。这时要指出**前置动作**是什么，并说明在前提没变之前该候选不可选。

**排除 ≠ 阻止**：阻止是「包没问题，只是前提还没满足」；排除是「这个包本身就不该出现在你的依赖里」。把两者混为一谈，用户可能以为只要升级 Node 就能用它。

### 第 4 步：输出建议（只给建议，不改文件）

本 skill 到此为止，不修改任何文件。改动由用户确认后另行发起。

推荐的输出结构：

```
## 结论
<pkg> <当前约束> → 建议 <版本>（放行 / 冲突 / 阻止 / 排除）

## 依据
- <命令> → <实际输出中支撑该结论的部分>
- 下载量：<周下载量数值>（低于门槛时写明判定与替代方向）

## 连带影响
- 需要同步调整的包与前置条件；没有就写「无」

## 若采纳，需要执行的命令
<仅供用户执行，本 skill 不代为执行>

## 未验证项
- 明确指出哪些判断来自推理而非命令输出
```

多包一起评估时，用「当前值 / latest / 候选 / 周下载量 / 判定」的对比表承载结论，把理由留在表下按包展开。把周下载量单列一栏，读者一眼就能看出哪些判定是被包级门槛拦下的，而不是被版本约束拦下的。

## 附带脚本

`scripts/downloads.js` 批量查询 npm 包的下载量并按门槛给出判定，省去逐个手敲 API。

```bash
node <skill-dir>/scripts/downloads.js vue vitest @vue/server-renderer
node <skill-dir>/scripts/downloads.js --min 50000 --json <pkg>...
```

它只读 npm 公开的 downloads API，不写任何文件。查询失败时不要用印象数字顶替——把「下载量」记进「未验证项」，并说明获取方式。

## 自检清单

输出前逐条对照，命中任何一条就回去补查询：

- 推荐里的版本号，是否每个都能指回一条命令输出？
- 评估的每个包，是否都查过周下载量，并把**真实数值**写进依据？
- 是否把「已在仓库里的依赖」和「准备新引入的包」混用了同一套门槛？（前者不应因下载量被硬排除）
- 被判「排除」的包，是否给了替代方向，而不是只丢一句「下载量太低」就结束？
- 下载量查不到时，是否写进了「未验证项」，而不是凭印象补一个数字？
- 是否把某个 `peerDependencies` 的兼容性当成了「同主版本所以 OK」？
- 联动簇里是否只动了其中一个成员？
- 是否有 `alpha` / `beta` / `rc` 混进了「建议」列？
- 跨主版本时，是否只说了「有破坏性变更」却没说具体影响哪些配置或 API？
- 是否把「阻止」误报成了「冲突」或「放行」？两者的行动成本不同，混淆会误导决策。

## 边界

- 只输出建议，不编辑 `package.json`、`pnpm-workspace.yaml` 或 lockfile。
- 命令结果是唯一事实来源；记忆、印象、其他项目的经验都不能替代查询。
- 下载量数值只来自 npm 官方 downloads API 或本 skill 的 `scripts/downloads.js`。查不到就标「未验证」，不凭印象估算。`workspace:` 包与私有源包没有公开下载量，不适用门槛。
- 下载量门槛默认取周下载 10,000，可用 `--min` 调整；调整时说明理由，别让它变成新教条。
- 查不到或输出不完整时，明说缺口并给出获取方式，不用推测填补。
- 不确定某个包是否值得升级时，说明「升级收益」与「升级成本」，把判断权交回用户。
