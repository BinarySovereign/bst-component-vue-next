# 提交信息编写规范

> 仓库全部提交统一采用「中文块 + 英文块 + 署名行」结构：两个语言块均为 `type: 描述` 标题行加逐条正文，中文块在上、英文块在下，署名行收尾。

> 提交信息统一保存在 `docs/commit-msg` 目录下，采用 `commit-msg-{1,2,3,....}.md` 格式进行命名。

## 定位与边界

| 维度 | 提交信息（commit message） | 变更日志（changelog） |
| --- | --- | --- |
| 粒度 | 一次提交 | 一个发布版本，聚合多次提交 |
| 受众 | 维护者、评审者 | 使用这个库的外部开发者 |
| 内容范围 | 改了什么、为什么改、内部实现细节 | 只保留使用方可感知的能力、行为与迁移信息 |
| 语言 | 中文块 + 英文块 + 署名行 | 与 README 一致，每个包一对中英文件 |
| 归属 | 整次提交 | 按发布包拆分，一个包一份 |
| 存续 | 随代码永久留存 | 随版本发布维护，历史条目只增不改 |
| 规范来源 | 本文件 | [changelog-rules.md](changelog-rules.md) |

### 提交信息承载的内容

| 内容 | 是否写入 | 位置 |
| --- | --- | --- |
| 本次做了什么 | 必须 | 标题行 |
| 为什么这么改、解决了什么问题 | 必须 | 正文条目 |
| 影响范围与破坏性变更 | 必须 | 正文单独成条，写明迁移方式 |
| 配套的测试、文档、构建改动 | 写入 | 正文条目 |
| 内部实现细节（模块、函数、文件） | 允许 | 正文条目，但须说明其影响 |
| 与本次提交无关的改动 | 禁止 | 拆分为独立提交 |
| 后续计划、`TODO`、`WIP` | 禁止 | — |
| emoji 与 Markdown 标题层级 | 禁止 | — |

- 判定标准是「这份提交信息能否让评审者不读 diff 就理解改动」，而不是「写了多少行」。
- 一次提交只描述一件事；当标题需要两个 `type` 才能概括时，说明本次提交应该拆分。

## 存放位置与命名

每次提交对应一份文件，文件名即序号，按提交顺序递增。

| 项 | 规定 |
| --- | --- |
| 目录 | 仓库根目录 `docs/commit-msg/` |
| 文件名 | `commit-msg-<N>.md`，`N` 为不含前导零的正整数 |
| 编号 | 从 `1` 开始连续递增，不跳号、不复用已删除的编号 |
| 编码 | UTF-8 无 BOM，行尾 LF（与 `.gitattributes` 对齐） |
| 数量 | 一次提交严格对应一份文件，禁止一次提交拆成多份 |
| 生命周期 | 文件提交后保留在仓库中作为历史记录，不随提交完成删除 |
| 使用方式 | 提交时用 `git commit -F docs/commit-msg/commit-msg-<N>.md` 直接读取 |

- 编号与提交一一对应：`commit-msg-1.md` 是第 1 次提交，`commit-msg-2.md` 是第 2 次提交，以此类推。
- 目录为空时首份文件从 `commit-msg-1.md` 开始；新增文件前先取当前最大编号再加一。
- 禁止把提交信息只写在仓库外的临时文件，导致编号与提交历史断档。

## 整体结构

> 一份提交信息由中文块、英文块与署名行组成：中文块在上、英文块在下，两块之间用独占一行的 `---` 分隔，署名行收尾。

```plaintext
<type>: <标题>

- <正文条目 1>
- <正文条目 2>
- <正文条目 3>

---

<type>: <say what you did in one line>

- <first thing you changed>
- <second thing you changed>
- <third thing you changed>

Copyright (c) <年份> <作者署名>. All rights reserved.
```

- 中文块在上、英文块在下，两块之间用独占一行的 `---` 分隔，分隔符前后各空一行。
- 每个语言块内部：标题行与正文条目之间空一行，条目之间不空行。
- 署名行只出现一次，固定在英文块之后。
- 两个语言块结构完全相同，只有语言不同：`type`、条目条数与条目顺序必须一致。

## 逐段落说明

> 以下条款同时约束中文块与英文块，两个语言块除语言外结构与约束完全一致。

### 提交类型

- 作用：标识本次提交的性质，便于检索历史与生成变更日志（生成规则见 [changelog-rules.md](changelog-rules.md)）。
- 取值：

| type | 适用场景 | 示例标题 |
| --- | --- | --- |
| `feat` | 新增功能、组件、对外能力 | `feat: 新增用户手机号验证码登录功能` |
| `fix` | 修复缺陷、异常行为 | `fix: 修复订单支付后状态未同步更新的问题` |
| `docs` | 文档、注释、README | `docs: 补充提交信息编写规范` |
| `style` | 样式与格式调整，不改动逻辑 | `style: 统一组件库缩进与分号风格` |
| `refactor` | 重构代码，不新增功能也不修缺陷 | `refactor: 重构组件注册逻辑` |
| `perf` | 性能优化 | `perf: 优化表格大数据量渲染耗时` |
| `test` | 测试用例与测试基建 | `test: 补充订单回调分支单元测试` |
| `build` | 构建脚本、依赖、产物配置 | `build: 升级 Vite 至 7.3.6` |
| `ci` | CI 配置与流水线 | `ci: 新增 Pull Request 校验流水线` |
| `chore` | 杂项，不改动源码与测试 | `chore: 清理仓库过期脚本` |
| `revert` | 回滚历史提交 | `revert: 回滚表格虚拟滚动改动` |

- 约束：
  1. 仅允许使用上表取值，小写英文，禁止自造类型。
  2. `type` 与标题之间固定用半角冒号加一个空格 `: ` 分隔。
  3. 一次提交只允许一个 `type`，中文块与英文块共用，跨类型改动必须拆分为多次提交。

### 标题行

- 作用：一句话说清本次提交「做了什么」，不点开详情即可理解改动。
- 约束：
  1. 两块标题均与各自 `type` 同行，采用动宾结构，末尾不加任何标点。
  2. 中文块标题为中文陈述句，不超过 30 字。
  3. 英文块标题为中文标题的口语化翻译，保持一行。
  4. 禁止「更新」「优化」「修改代码」等无信息量描述。
  5. 涉及模块名、组件名时保留其英文原名。

### 正文条目

- 作用：逐条展开改动关键点，覆盖改了什么、为什么改、影响什么。
- 约束：
  1. 每条以 `- ` 开头、独占一行，末尾不加标点。
  2. 中文块至少 1 条，建议 2～5 条，按重要性降序排列。
  3. 英文块条目为中文块条目的逐条口语化翻译，条数与顺序一一对应。
  4. 一条只写一件事，禁止把多个改动揉进同一条。
  5. 存在破坏性变更时必须单独成条，写明影响范围与迁移方式。
  6. 禁止只复述标题，条目须提供标题之外的信息。

### 署名行

- 作用：声明本次提交的版权归属。
- 格式：`Copyright (c) <年份> <作者署名>. All rights reserved.`
- 约束：
  1. 固定为提交信息最后一行，位于英文块之后，与英文块之间空一行。
  2. 全文只出现一次。
  3. 年份取提交当年；`<作者署名>` 替换为实际提交者的个人或团队名称。

## 完整示例

### 新增功能

```plaintext
feat: 新增用户手机号验证码登录功能

- 新增验证码发送接口，支持6位数字随机验证码生成
- 增加验证码有效期控制，默认5分钟过期
- 前端增加验证码输入组件，对接后端登录接口
- 更新接口文档，补充验证码登录相关参数说明

---

feat: add phone number verification code login

- add a code sending API with random 6-digit codes
- codes expire after 5 minutes by default
- add a code input component and hook it up to the login API
- update the API docs with the new login parameters

Copyright (c) 2026 Author Name. All rights reserved.
```

### 修复缺陷

```plaintext
fix: 修复订单支付后状态未同步更新的问题

- 修复支付回调异步处理超时导致订单状态未变更的问题
- 增加回调失败重试机制，最多重试3次
- 添加异常日志打印，方便定位回调处理失败场景
- 单元测试补充订单回调分支用例

---

fix: fix order status not syncing after payment

- fix the payment callback timing out and leaving the order status unchanged
- retry failed callbacks up to 3 times
- add error logs to make failed callbacks easier to trace
- add unit tests for the order callback branches

Copyright (c) 2026 Author Name. All rights reserved.
```

### 重构

```plaintext
refactor: 重构组件注册逻辑

- 将注册表从组件内部抽出为独立模块
- 注册流程改为同步执行，首帧即可完成注册
- 删除已废弃的异步注册分支

---

refactor: rework the component registration logic

- pull the registry out of the component into its own module
- make registration synchronous so the first frame registers everything
- drop the deprecated async registration branch

Copyright (c) 2026 Author Name. All rights reserved.
```

## 编写流程

1. 先用 `git status` 与 `git diff` 确认本次改动范围，判断能否归入同一个 `type`。
2. 按「提交类型」取值表选定 `type`，写出中文标题：一句话、动宾结构、不超过 30 字、不加标点。
3. 逐条列出中文正文，覆盖改了什么、为什么改、影响什么；破坏性变更单独成条。
4. 把中文块逐条翻译成英文块，保持 `type`、条数与顺序一一对应。
5. 补上 `---` 分隔符与署名行，确认中文在上、英文在下、署名行收尾。
6. 存入 `docs/commit-msg/commit-msg-<N>.md`，先用 `node scripts/ci/check-commit-msg.js --msg <N>` 校验，通过后用 `git commit -F` 提交，再对照「提交前自检」核对一遍。

## 反例

| 反例 | 问题 |
| --- | --- |
| `更新代码` | 缺少 `type` 与正文，标题无信息量 |
| `feat：新增登录功能` | 使用中文冒号，分隔符必须为半角 `: ` |
| `feat: 新增登录功能。` | 标题末尾多写标点 |
| `fix: 修复bug` | 标题笼统，未说明修复内容 |
| `feat: 新增登录功能`（仅有标题行） | 缺少正文条目、英文块与署名行 |
| 只有中文块、没有英文块 | 一份提交信息必须同时包含中文块与英文块 |
| 英文块写在中文块之前 | 顺序固定为中文在上、英文在下 |
| 中文块与英文块的 `type` 不一致 | 两个语言块必须共用同一个 `type` |
| `feat: 新增登录功能 fix: 修复登录失效` | 一次提交混入多个 `type`，需要拆分 |
| 中文块与英文块之间缺少分隔符 | 两块之间必须用独占一行的 `---` 分隔 |
| 中文块 3 条正文、英文块 2 条 | 两块条目条数与顺序必须一一对应 |
| `feat: 新增登录功能 ✨` | 提交信息不使用 emoji，emoji 仅用于变更日志的分组标题 |
| `### 新增` / `## [1.0.0]` | 混入了变更日志的标题写法，提交信息不使用 Markdown 标题层级 |
| `commit-msg-0.md`、`commit-msg-new.md` | 文件名必须是连续递增的 `commit-msg-<N>.md` |
| 署名行保留 `Author Name` 占位符 | 必须替换为实际提交者署名 |

## 强制约束清单

1. 提交信息固定为「中文块 → 英文块 → 署名行」，中文在上、英文在下，两块之间用独占一行的 `---` 分隔，署名行只出现一次且位于最后。
2. 标题行固定为 `type: 标题`，中文块与英文块共用同一 `type`，仅允许取值表中的 11 个取值。
3. 中文标题不超过 30 字，中英两块标题均末尾不加标点、禁止无信息量描述。
4. 中文正文至少 1 条；英文正文为逐条口语化翻译，条数与顺序与中文一致。
5. 破坏性变更必须单独成条，写明影响范围与迁移方式。
6. 一次提交只允许一个 `type`，跨类型改动拆分为多次提交。
7. 每次提交对应一份 `docs/commit-msg/commit-msg-<N>.md`，编号从 `1` 起连续递增，UTF-8 无 BOM + LF，提交后用 `git commit -F` 读取。
8. 提交信息不使用 emoji，也不使用 Markdown 标题层级：emoji 只用于变更日志的分组标题，`#` / `###` 只用于变更日志的版本与分组标题。
9. 两个语言块的 `type`、条目条数与条目顺序必须一一对应，禁止只改其中一块。

---

## 提交前自检

1. `type` 是否在取值表内，中文块与英文块是否一致，分隔符是否为半角 `: `。
2. 中文标题是否一句话说清改动、是否超长或带句末标点。
3. 英文块是否为中文块的口语化翻译，条目条数与顺序是否一一对应。
4. 中文块是否在上、英文块在下，两块之间是否有 `---` 分隔符与空行，署名行是否处于最后一行且只出现一次。
5. 本次改动是否只对应一个 `type`，是否需要拆分提交。
6. 文件是否存于 `docs/commit-msg/`，编号是否为当前最大编号 `+ 1`，是否已执行 `node scripts/ci/check-commit-msg.js --msg <N>` 并通过。
7. 是否误用了 emoji、Markdown 标题层级或变更日志的分组写法。
8. 署名行的年份与实际提交者是否已替换，是否残留 `Author Name` 占位符。
